1 · State machine and communication graph

First which state the system is in and what moves it, then what flows in each of them. Boxes and edge labels in every diagram are links into sections 2 and 3.

1.1 · State machines

Three machines run at once and they are not nested: the flight mode owns the vehicle, the governor owns the reference, and a three-layer freshness chain owns the arm's torque. Only the first can hurt you — the other two degrade to a hold.

1.1.1 · Flight mode — the one that owns the vehicle

Six states, and only four transitions you can command. Everything drawn dashed red happens on its own.

on the ground SAFETY — PX4 flies it DIRECT — the node flies it waiting on something failsafe / refused

1.1.2 · Reference governor — only alive inside DIRECT

This is the machine you actually drive during a flight, and every state of it is printed verbatim on whole_body_governor/status. Nothing here moves the vehicle until you press Send — a planned transition sits in PLANNED indefinitely, still streaming the hold.

Segment a bag on this. status is a latched String and its edges are the only clean phase boundaries in a whole-body flight — the reference stream itself never stops.

1.1.3 · Arm torque source — three gates in series

A torque stream must never latch, so both downstream layers drop authority rather than hold the last commanded value. They fall back to a position hold, which is safe to latch.

Both fallbacks are hysteretic: 0.3 s of silence drops out, and 3 consecutive fresh commands are needed to re-engage — so a marginal stream cannot chatter between the two.

The controller owns position, attitude, rate, mixing and the four joint torques; PX4 runs no control law. The governor becomes the source of the reference, the ground-station setpoint becomes a pending target, and vehicle_attitude_setpoint goes silent.

Captured ONCE, on the SAFETY → DIRECT edge, as a rest spec (x_b, φ, q). Rates

The arm's control frequency is update_rate in the controller_manager block, not a topic setting. It drives the whole ros2_control cycle — read(), every controller's update(), then write() — and joint_states inherits it.

Control loop250 Hzupdate_rate, in every config except the two Gazebo torque files, which run at 1000.
joint_states250 HzThe broadcaster has no rate parameter — it publishes once per cycle, so update_rate IS this topic's rate.
smoothed reference250 Hzstate_publish_rate in torque_controller_isaac_aerial.yaml is 250.0 — NOT the 50 Hz the position-mode config uses. It is the arm controller's own min-jerk path; nothing on the reference path reads it.
Isaac feedbackcapped upstreamread() latches the last cached sample. The Isaac publisher must keep up, or the fast loop re-reads stale data.

The prefix names the owner

Read a topic and you know which subsystem produced it, with no lookup. The split between the two arm prefixes is decided by one question: does this topic still exist, unchanged, when the real arm is plugged in?

Real arm stackfsc_open_manipulator/ros2_control. These exact names appear on the hardware bench too. Applications live here.
Simulator onlyisaacsim_manipulator/Stands in for the Dynamixel/U2D2 wire. Absent on hardware — that absence IS the sim/hardware distinction.
Flight controllerfsc_autopilot_ros2/The same convention, already in use — this scheme just extends it to the arm.

Open hazard: effort does not mean the same thing on every backend

Tier A promises identical data across backends. For the effort field on joint_states, that promise is currently false: Isaac publishes N·m, the Dynamixel hardware publishes raw counts (XM430-W350: 1 count ≈ 2.69 mA), and Gazebo publishes 0.0 always.

Nothing reads effort today — the CoM feedforward uses position only — so this is latent. It stops being latent with torque mode, since the real arm runs its Dynamixels in current mode. The fix is conversion inside the Dynamixel SystemInterface; until then, treat effort as backend-specific.
