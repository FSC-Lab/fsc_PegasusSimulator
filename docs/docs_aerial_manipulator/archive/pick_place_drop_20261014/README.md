## The payload (`tools/assembly_stl_to_usda.py` → `assets/Box_Payload_Assembly.usda`)

`/usr/bin/python3 tools/assembly_stl_to_usda.py`. The STL holds separate closed shells; the
converter tells them apart by shape and refuses a file that does not fit (basket = the
largest; holder = the 115 × 30 × 181.5 mm shell; markers = five 30 × 30 × 55 mm shells;
brackets = the rest) and checks the holder has NO arch (its top no wider than the 3 mm fin).

- Frame as the other CAD payloads: origin = the basket centre (obj_0), +z up, +x = the
  claw's slide-in direction, +y = the jaws' closing axis.
- **The flag (fin) points AWAY from the basket centre, i.e. TOWARD the vehicle**: flag
  x −47.5 … −27.5 mm, stem x −27.5 … −17.5 mm, both 3 mm thick, flag 149.5 … 199.5 mm above
  the basket centre.
- **It is 306 mm wide across the jaws' axis** (the two side marker balls, y ±153 mm) and
  227 mm along x. The bin is 290 mm wide outside (~285 inside), 371 mm long.
- Colliders: basket box + boxes over its arms; the holder exactly (prisms); markers as
  sphere + post; brackets as boxes. 200 g, markers 3 g each, CoM (−0.8, 0.0, 7.7) mm.
- The same invisible 20 mm grip pad as the holder (`PEGASUS_PNP_FIN_GRIP_MM`): the sim claw
  cannot close below ~19 mm.

## The planner (fsc_trajectory_planner)

- `pick_place_place_drop` (bool): execute_place flies straight to the place claw target
  (+ `pick_place_drop_height`) and ENDS there — no vertical approach, no descent; the leg
  completes on the drop point ("DONE execute_place next=exit_place (open the gripper first)");
  a descent request is refused; Exit To Place backs off `pick_place_place_exit_back` and
  climbs `pick_place_approach_dz`.
- `pick_place_drop_height` default **0.0** (user's workflow: Get the basket on the box's
  COVER, type z + 0.05 → the place point IS the release point); a positive value raises the
  release further; negative is refused. gtest
  `ADropPlaceEndsOnTheDropPointWithNoDescentAndBacksOut` covers both; 26/26 pass.

## The automatic Exit To Drop did not fire in Isaac: the sim gripper's OPEN reported a jam (2026-10-15)

- **Symptom (user, windowed sim):** 4.2 Drop opened the gripper but 4.3 Exit To Drop never started. Arm GS
  log: `Gripper OPEN did not complete (aborted, stalled -- mechanism jammed?)`; the Isaac gripper action
  server: `stalled at -16.3 deg (target +0.0)`. The GS starts the exit only on a SUCCEEDED open (a stalled
  open is treated as a jam, correctly), so nothing followed.
- **Cause, in the plant (06):** the gripper bus slews its target at `GRIPPER_RATE` (0.5 rad/s) from the LAST
  COMMANDED angle. After a close that stalls on the payload (here -16 to -40 deg), that target sits at the
  close command (-50 deg), so an OPEN first ramps through the empty band down to where the fingers are, and
  the fingers do not move for (stall angle + 50 deg) / 28.6 deg/s -- 1.2 s from -16 deg. The action
  server's stall test (< 1 deg over 0.3 s) fires first and aborts the goal.
- **Fix (06, `_on_gripper_command` / `_step_gripper`):** a NEW command restarts the slew from the MEASURED
  finger angle, so the fingers move on the first step. The same command repeated (the action server
  re-sends one target per goal) does not restart it. The real gripper has no such slew, so this is
  sim-only.
- **Driver:** `pnp_mission_v2.py --grip-via-action` now also OPENS through the GripperCommand action on a
  drop (`gripper_action_open`, `--grip-open-m` 0.019 = the GS's `gripper_open`) and aborts unless it
  SUCCEEDS -- the same rule the GS applies -- so a headless run exercises the GS's path.
- **tray5** (`PNP_DRIVER_ARGS="--drop-place --grip-via-action --grip-axis-tol 0.003"`): close stalled at
  -32.5 deg (the grasp); open SUCCEEDED, reached in 1.14 s; exit started 0.5 s later from the measured
  position (138 mm back from the release hold), backed out 10 cm and climbed 20 cm; payload flat in the
  tray (-0.977, -0.974, 0.813), tilt 0.0 deg; mission complete.
- **Payload colliders (user question):** `Box_Payload_Assembly.usda` carries colliders for the basket, the
  holder, the brackets AND the 5 marker posts + balls, matching the visuals; the ball resting near the tray
  rim in the user's screenshot is a side marker on the camera side at basket-bottom height, not a gap.

### The drop offset, identified (2026-10-15, user request)

The decoupled rig's release error is ~consistent, so it is cancelled by shifting the Drop point --
nothing else in the task changes. `tools/make_drop_offset_yaml.py` writes a copy of the pick-and-drop
planner yaml with only `pick_place_place_point` shifted; `run_pnp.sh` takes it as `PNP_PLANNER_YAML`
(geo). `tools/drop_offset_id.py` measures, per run, where the payload is released relative to the
COMMANDED drop point (it checks that point against the recorded claw reference at the hold: 0.0 mm in
every run). The payload rides rigidly in the gripper, so its position at each moment of the hold is
where it would be released if Drop were pressed then: the four new runs held 5 s (`--drop-dwell 5`).

**Which directions matter (corrected):** only the payload's parts below the 35 mm wall can catch it
when it lands flat -- the basket (x, y +-55 mm), its arms (y +-117.5) and the two SIDE marker balls
(y +-153, at the basket's bottom). The front / back balls (x +-113) sit 47.5 mm above the bottom and
pass over the wall. So the tray leaves **~30 mm a side across the vehicle (y) and ~87 mm along the
heading (x)**; the y error decides flat or not. The footprint used before (227 x 306 mm, every marker)
said x was the tight side, which is wrong for this tray. For the same reason the drop's ~4 deg of yaw
error costs ~1 mm in y: no yaw correction is needed.
